# Research: node operating model (2026-11-21)

Five topics, each researched by one agent and fact-checked against primary sources by an independent skeptic agent.
Verdict = the fact-checker's result. Use 'partially_supported' / 'unsupported' / 'wrong' claims only with their correction.

## win-throttling

Windows has no single mechanism that makes a child workload invisible to the student. The documented tools stack in layers, and each covers a different resource. (1) CPU priority: IDLE_PRIORITY_CLASS (thread base priority 4) or BELOW_NORMAL (6). This is strict preemptive priority, so a student's normal-class threads (base 8, plus foreground and input boosts) always run first. You can set it per child via CreateProcess/subprocess creationflags, enforce it through a job with JOB_OBJECT_LIMIT_PRIORITY_CLASS, and change it at runtime with SetPriorityClass. Microsoft states plainly that CPU priority is not enough: "even an idle CPU priority process can easily interfere with system responsiveness when it uses the disk and memory". (2) The documented fix for disk and memory, PROCESS_MODE_BACKGROUND_BEGIN, works only on the current process. The agent cannot apply it to a child; the workload (or a UDCS-controlled bootstrap inside it) must call it itself. (3) Memory priority (ProcessMemoryPriority) and EcoQoS (ProcessPowerThrottling) are set with SetProcessInformation, which takes a handle with PROCESS_SET_INFORMATION. So the agent can apply both to a child it owns, and change them at runtime. EcoQoS mainly lowers frequency and power, which helps heat and fan noise. Its exact effect on non-hybrid lab CPUs without battery is not documented. (4) Job Objects are UDCS's main control surface. They provide CPU rate control (hard cap, weight 1-9, or min/max, from Windows 8), a commit-memory cap with no OOM-kill (allocations fail), KILL_ON_JOB_CLOSE for orphan cleanup, scheduling class, affinity, and accounting. SetInformationJobObject is documented as a way to change a subset of limits on an existing job, which makes "tighten the cap when the student becomes active" a plausible design. That still needs a test on a running job. (5) Per-job I/O rate control (SetIoRateControlInformationJobObject) is marked by Microsoft as "not supported" on Windows 10 1607 and newer, so UDCS must not rely on it. (6) There is no documented, supported Win32 API to freeze a whole job. NtSuspendProcess and JobObjectFreezeInformation are undocumented. DebugActiveProcess suspends only during attach and makes the target die if the debugger exits. SuspendThread is documented as "primarily designed for use by debuggers" with deadlock risks, although BOINC does exactly this: a Toolhelp thread snapshot plus SuspendThread/ResumeThread. Cooperative suspension (signal the workload, let it checkpoint) should be the primary path. A hard cap of near 0% or thread suspension should be the fallback. (7) CPU Sets are soft, and true core reservation exists only on "some versions" of Windows. Hard affinity through the job (JOB_OBJECT_LIMIT_AFFINITY) reliably keeps the workload off N cores, but it also wastes them while the student is idle. (8) No documented knob controls the remaining interference channels: memory bandwidth, LLC sharing, SMT-sibling contention, GPU, and thermal headroom shared across cores. Only fewer active cores, a hard CPU cap, and EcoQoS reduce them indirectly. UDCS therefore needs measurement-driven throttling, not just priority. All of these APIs can be called from Python 3.12 through ctypes or pywin32. However, subprocess.Popen does not expose the primary thread handle, so the robust launch path (CREATE_SUSPENDED, assign the job, resume, or PROC_THREAD_ATTRIBUTE_JOB_LIST) requires calling CreateProcessW directly.

**Missed points raised by the fact-checker:**

- Turn off priority boosting for the workload. A thread at IDLE/NORMAL (base 4) is boosted after an I/O or wait completes and can briefly preempt the student's base-8 threads. SetProcessPriorityBoost(hWorkload, TRUE) is the documented control and can be applied from outside the process. Nothing in the findings pins thread-level priority; job PRIORITY_CLASS does not stop SetThreadPriority(TIME_CRITICAL), so the agent should also periodically check workload threads' base priorities.
- Resident-memory caps exist and were missed. JOB_OBJECT_LIMIT_WORKINGSET (0x1) with Minimum/MaximumWorkingSetSize sets a per-process working-set limit (most restrictive in a nested chain). This is the documented lever against the workload's resident pages pushing out the student's pages, in addition to the commit cap and memory priority. Its paging cost to the workload must be measured.
- JobObjectNetRateControlInformation (class 32, Windows 10+) is a documented network-bandwidth limit for jobs, listed on the SetInformationJobObject page. It matters when workloads download datasets or checkpoints on a shared lab network, now that disk I/O rate control is unavailable.
- Detecting interactive use from session 0: the agent will run as a service in session 0. Per-session input-idle APIs (GetLastInputInfo is documented as not system-wide across sessions) will not see the student's activity from session 0. A design is needed that does not depend on it: a per-session helper, WTS session state, or pure pressure-based signals such as CPU ready/queue length and memory, all as admin policy decides. Not verified in this check; open question.
- KILL_ON_JOB_CLOSE conflicts with 'automatic workload resumption' and service recovery. An agent crash or service restart kills every workload. Options: keep the only job handle in a tiny, stable supervisor process separate from the Python agent; or create a named job without KILL_ON_JOB_CLOSE and reopen it with OpenJobObject after restart (only named jobs can be opened). Both have different crash-safety trade-offs and need a decision record.
- GPU contention is not covered by any of these CPU, memory or job mechanisms. CUDA on GeForce runs under WDDM, where long kernels compete with the student's desktop composition and are subject to the TDR watchdog. CPU priority, job caps and EcoQoS do nothing for GPU timeslicing or VRAM pressure. This needs separate research: NVML utilization/memory monitoring, kernel-duration limits, and checkpoint-then-release rather than suspend-while-holding-VRAM.
- EcoQoS and Utility QoS give little or no benefit on Windows 10 lab PCs and on non-hybrid desktop CPUs on AC power. The throttling design must not rely on QoS as a primary lever. The job hard cap, idle priority, boost disable and working-set limits are the portable set across Windows 10 and 11.
- Low-memory signalling: the findings cover limits but not detection. Windows has documented memory resource notifications (CreateMemoryResourceNotification / QueryMemoryResourceNotification) that the agent could use as a pressure trigger to throttle or checkpoint. Its exact semantics were not verified here.
- Monitoring workload I/O: QueryInformationJobObject with JOBOBJECT_BASIC_AND_IO_ACCOUNTING_INFORMATION (listed on the Job Objects page) gives job-wide I/O counts. Without kernel I/O rate control, this supports agent-level detect-and-pause for disk I/O.

## interactive-detection

A session-0 service cannot see student input directly. GetLastInputInfo only reports the calling session's input, and impersonating the user does not change that. On this Win11 22000 machine, WTSINFOEX_LEVEL1.LastInputTime came back as 0 for the physical console session (tested). The reliable design therefore has two layers. Layer 1: the service itself reads the coarse signals that ARE documented as reaching session 0. These are SERVICE_CONTROL_SESSIONCHANGE (logon, logoff, lock, unlock, console connect), WTSSessionInfoEx SessionFlags for lock state, GUID_GLOBAL_USER_PRESENCE (sent only to session-0 programs), GUID_CONSOLE_DISPLAY_STATE, and per-process GPU load from PDH '\GPU Engine(*)\Utilization Percentage', whose instance names carry pid_ (tested working on a GT 730 plus Intel iGPU). Layer 2: a tiny unprivileged per-user helper reports fine-grained interactivity over a named pipe whose DACL is restricted. HTCondor (condor_kbdd via the HKLM Run key) and BOINC (boinctray.exe) both use this helper pattern, and Raymond Chen recommends it. The helper reports idle seconds from GetLastInputInfo and the SHQueryUserNotificationState value (QUNS_BUSY / RUNNING_D3D_FULL_SCREEN / PRESENTATION_MODE). BOINC's implementation is a negative example: it uses a NULL-DACL Global\ file mapping that any process can write. NVML per-process accounting is not a viable basis on GeForce with WDDM. On the local GT 730 (driver 456.71), utilization, process lists, process utilization and accounting all returned NOT_SUPPORTED (tested). NVML documents usedGpuMemory as always unavailable under WDDM, and it classes all GeForce parts as 'Limited Support'. So student GPU contention should be measured with the WDDM PDH counters, which are vendor-neutral and need WDDM 2.0 or later. NVML stays for device-level data where it works. For privacy, the helper and service should export only derived, aggregate signals (idle bucket, busy/fullscreen flag, interactive GPU share). They should never export window titles, process names of student apps, or keystroke timing to the controller. That rule is a proposed design, not a sourced standard.

**Missed points raised by the fact-checker:**

- Fail-safe direction. Several mechanisms report 'idle' when data is missing. Examples: BOINC returns time-since-boot when the shared memory is absent; a session-0 GetLastInputInfo call sees no input. UDCS must treat 'helper not running or not reporting' as 'student present, run at the most conservative throttle', never as 'idle'.
- Input idleness is not the same as interactive demand. A student rendering, compiling or training a model may give no input for minutes while the machine is under heavy load. Capacity decisions must combine the input and presence signal with real resource pressure from non-UDCS processes. Signals include per-PID PDH GPU Engine utilization minus UDCS PIDs, CPU utilization or processor queue length, memory commit or available bytes, and disk queue. Gating on input alone either starves UDCS or interferes with the student.
- Trust model for helper IPC. Any value a user-session helper sends is under that user's control. Design it so forged values can only make UDCS more conservative, for example by honouring 'present/busy' immediately and requiring sustained, corroborated evidence for 'idle'. Attribute each client with GetNamedPipeClientProcessId/SessionId so one session cannot speak for another.
- Per-session helpers can use GUID_SESSION_USER_PRESENCE, GUID_SESSION_DISPLAY_STATUS and WTSRegisterSessionNotification (all documented for user-mode interactive apps). These give per-session presence that complements GUID_GLOBAL_USER_PRESENCE in the service.
- Multi-session machines: fast user switching, disconnected sessions and RDP. Policy must define whose activity counts. A disconnected session's background processes still create load even with no input. WTS_SESSION_REMOTE_CONTROL plus GetSystemMetrics(SM_REMOTECONTROL) should be considered so an IT remote-support session is treated as interactive.
- Helper footprint. A Python interpreter per logged-on session costs tens of MB of RAM and startup time on every logon. A small native helper (C/C++/Rust) is more consistent with the 'minimal overhead, student never notices' requirement. This is an assumption to be measured, not a verified figure.
- Event-driven over polling. Combine SESSIONCHANGE, POWEREVENT/GUID_GLOBAL_USER_PRESENCE and GUID_CONSOLE_DISPLAY_STATE pushes with low-frequency polling of PDH and helper data, and add hysteresis to avoid suspend/resume flapping. None of the findings proposes debounce or hysteresis parameters, or a test to tune them.
- Whether RegisterPowerSettingNotification delivers an initial current-state notification on registration is not stated on the pages opened. It must be tested, or state must be seeded at service start by other means.
- No finding verifies the lock-screen and secure-desktop (Winlogon, UAC) behaviour of GetLastInputInfo in the helper, i.e. whether input on the lock screen or UAC prompt updates the user session's last-input tick. This affects 'locked but actually in use' detection.
- GPU contention with the student is the hardest case on GeForce/WDDM. Even with accurate detection, a running CUDA kernel cannot be preempted on UDCS's terms. Detection latency plus kernel duration determines how much stutter the student sees. Kernel-duration limits, or chunking workloads into short kernels, belongs in this design, and is untested.

## gpu-sharing

On Windows lab PCs every GeForce card runs under WDDM. TCC is not available on GeForce (GTX Titan excepted), and TCC would also disable the display. MPS is Linux/QNX only, and MIG exists only on A100/A30/H100/Blackwell data-center and RTX PRO parts. So no NVIDIA mechanism exists for safe, isolated GPU sharing on these machines: a UDCS CUDA job and the student's desktop, browser, games and CAD share one GPU through the WDDM scheduler. Under that scheduler, any packet that cannot be preempted within TdrDelay (2 s by default) triggers a TDR GPU reset. Microsoft says end users and applications should not change these keys, so UDCS must design for short kernels, not raise TdrDelay. Compute preemption granularity varies by GPU and driver. NVIDIA's Pascal Tuning Guide promises instruction-level compute preemption only for GP100, and there is a forum report of a GeForce Pascal card reporting no compute preemption on Windows. The agent must therefore measure cudaDevAttrComputePreemptionSupported on each node rather than assume it. A per-process GPU priority API exists: D3DKMTSetProcessSchedulingPriorityClass, a documented WDK thunk exported from gdi32.dll that takes a process handle. Whether it actually de-prioritises CUDA work on NVIDIA WDDM drivers, with or without HAGS, is undocumented and must be tested. VRAM held by a CUDA process under WDDM is a request to the WDDM memory manager, so it can be paged to system memory. This 'protects' the student only by making both sides slower, and the CUDA unified-memory oversubscription path is officially not available on Windows. NVIDIA's transparent checkpoint (cuCheckpoint* driver API, cuda-checkpoint utility) is officially 'restricted to Linux'. On Windows, 'pause a GPU job' can honestly mean only these things: (a) throttle the job (smaller batches, sleeps between kernels, lower GPU priority if the experiment shows it works); (b) at the next safe point, cooperatively checkpoint at application level (model, optimizer, scheduler, GradScaler, RNG state, data-loader position via torch.save) and then either free VRAM by exiting the process, or merely park it with torch.cuda.empty_cache(), which frees only cached, unoccupied memory; (c) resume from the checkpoint later, possibly on another node. Freezing the process's threads stops new kernel submission but does not return VRAM. The reclaim protocol has to be cooperative (agent signals, job checkpoints within a bounded deadline), and hard kill is the fallback once that deadline passes. Hardware triage matters too. The GT 730 (cc 3.5 Kepler, or cc 2.1 Fermi for the DDR3 128-bit variant) is unsupported since CUDA 12.0, and current PyTorch CUDA 13 wheels require Turing (sm_75) or newer. Kepler nodes should be CPU-only in UDCS, and GPU eligibility should be gated on compute capability 7.5 or higher for prebuilt PyTorch.

**Missed points raised by the fact-checker:**

- The WDDM TDR watchdog applies to CUDA on every GeForce display GPU (kernelExecTimeoutEnabled=1). Under the default TdrDelay of 2 s, a CUDA kernel or DMA packet that cannot be preempted in time triggers a TDR, which resets the display driver for the student. UDCS GPU jobs therefore need a policy cap on kernel duration (short kernels, chunked work), not just a GPU time-slice, and UDCS must never 'fix' this by changing TDR keys, which Microsoft reserves for driver development.
- The design is missing a way to measure the student's own GPU demand. Candidates include the Windows 'GPU Engine' / 'GPU Process Memory' performance counters (per-process, per-engine utilization in Task Manager) and NVML per-process utilization. The researcher did not verify which work under WDDM for the agent running in session 0. NVML per-process memory is commonly reported as N/A under WDDM; this needs a test on real lab hardware.
- Whether CUDA contexts can be created at all from a process launched by a session-0 Windows service (or by a child of one) on a WDDM GeForce GPU was not checked. It is a prerequisite for the whole GPU-sharing design and should be verified by a small experiment on an RTX 3060 / 4060 Ti node.
- There is no OS- or driver-level GPU preemption guarantee for CUDA on GeForce/WDDM that UDCS can rely on. Suspension therefore has to be cooperative: the job checkpoints at safe points, releases its CUDA context and VRAM (torch.cuda.empty_cache alone is not enough), and the agent stops submitting new work. Driver-level checkpointing (cuda-checkpoint) and MPS/MIG are all unavailable on Windows GeForce, so per-workload checkpoint cost has to be built into scheduling decisions.
- The VRAM pressure signal is missing. Because WDDM silently pages CUDA allocations to system memory instead of failing, a UDCS job can steal VRAM from the student's foreground app, or itself slow down drastically, without any error. The agent needs to watch the per-process budget and usage (e.g. DXGI QueryVideoMemoryInfo, where callable, or NVML device memory). Pinning per_process_memory_fraction well below VRAM should be evaluated rather than assumed to protect the student.
- GPU sharing on Windows consumer cards is effectively whole-device time-sliced. Without MPS or MIG, a UDCS job and the student's apps share the scheduler, and isolation is weak. For the operating model, the safest Phase-1 policy is probably to run GPU work only when there is no interactive GPU demand, or only when no interactive session is active, with the CPU workload using the user's existing throttling path. Fine-grained concurrent GPU sharing with an active student belongs in a later phase, after measurement.
- Heterogeneous capability gating needs a support matrix maintained by the controller. The GT 730 (CC 3.5 or 2.1) is excluded from CUDA 12+, and current PyTorch wheels require Turing or newer. The node agent should report compute capability, driver version, the driver model (WDDM), and whether HAGS is enabled, and the controller should refuse to place jobs on unsupported nodes rather than fail at runtime.

## prior-art

I read the primary sources: HTCondor's policy docs, its Windows platform page and release notes, BOINC's preferences wiki and client/API source, and Microsoft Learn. Both mature systems show that "borrow without disturbing the owner" is a policy engine evaluated on a short loop, not a single idle switch. HTCondor's Desktop template moves through Busy -> Suspended -> Preempt (vacate) -> Kill, with timers between the stages. Its inputs are KeyboardIdle and NonCondorLoadAvg (LoadAvg minus CondorLoadAvg), which keeps the guest job's own load out of the "is the owner busy" signal. UDCS should copy that separation directly. BOINC adds graded limits for the in-use and not-in-use cases (CPU percentage, CPU time, memory, and suspend when non-BOINC CPU is above X), cooperative checkpointing through its API, and an option to leave suspended tasks in memory. Its CPU-time limit is a 1-second whole-task suspend/resume duty cycle, and the developers' own attempt to make it finer was shelved. On Windows 8 and later, UDCS should use Job Object CPU hard caps instead (verified API). Two Windows lessons matter most for UDCS. First, a service in session 0 cannot see user input: HTCondor needs a per-user condor_kbdd started from the HKLM Run key, and GetLastInputInfo is session-scoped by Microsoft's own documentation. So the UDCS agent needs a tiny per-session helper (or an equivalent) for idle detection. Second, BOINC users historically lost GPU computing when BOINC ran as a Windows service because of session 0 isolation. Whether CUDA works from session 0 on modern WDDM GeForce drivers is unverified, so it must be tested on the actual GT 730, RTX 3060 and RTX 4060 Ti machines before committing to a session-0-only design. Suspended GPU work is handled differently: BOINC always removes suspended GPU tasks from memory once they are no longer scheduled, rather than holding VRAM. UDCS should plan for GPU preemption by checkpoint-and-exit, not by freezing the process. HTCondor's standard universe (transparent checkpointing) is gone; checkpointing is now the application's job, by exiting with a designated code. UDCS should adopt the same contract: an exit code or signal plus checkpoint files, with no attempt at transparent process checkpointing.

**Missed points raised by the fact-checker:**

- CUDA from session 0 on GeForce/WDDM is the single biggest architectural risk for UDCS GPU workloads. There is no NVIDIA documentation confirming it works, and recent forum reports (cudaGetDeviceCount error 100 in a service until a user logs in) suggest it may not work reliably. - Neither HTCondor nor BOINC uses GPU pressure for desktop policy (no GPU utilization in SUSPEND/START, and BOINC only offers a binary 'suspend GPU when in use'). UDCS must define GPU yielding itself (cooperative pause at kernel boundaries, NVML utilization and foreground-process sampling).
- The input-idle signal must come from a per-session helper (as condor_kbdd does), because GetLastInputInfo is session-scoped. Design it to fail safe: a missing or stale helper heartbeat should count as 'user present / busy', not idle. This avoids HTCondor's fail-toward-idle mode.

Memory and IO pressure are as student-visible as CPU. None of these was verified here.
- The BOINC and HTCondor Windows suspend primitives (SuspendThread on a worker thread, whole-task suspend) keep the job's RAM and VRAM resident. On 8-16 GB lab PCs a suspended ML job holding GPU memory still harms the student, which is why BOINC unloads throttled GPU jobs. UDCS needs a policy for evicting suspended memory and VRAM, not just pausing.
- BOINC's 1-s duty-cycle throttling causes visible usage oscillation and was tied to API polling. Kernel-enforced Job Object CPU caps (Windows 8+) are a better fit than duty cycling for CPU work, but the cap's scheduling interval is undocumented and should be measured.
- The researcher did not cover Slurm or other prior art for cycle-scavenging on interactive desktops (e.g. HTCondor's Windows run accounts and the security model for running untrusted student and researcher code under LocalSystem-spawned low-privilege accounts, AppContainer, or Windows Sandbox). Security isolation of jobs from the logged-in student's files is a core requirement.

## service-ops

The SCM gives UDCS most of what it needs. With that, the agent can be a small Python service that defers to the student, provided the configuration is deliberate. Recommended setup: Automatic (Delayed Start), so the SCM starts it after the other auto-start services, with ServiceMain at THREAD_PRIORITY_LOWEST. Recovery actions should be set to restart, and SERVICE_CONFIG_FAILURE_ACTIONS_FLAG set to TRUE, so a clean exit with a non-zero exit code also triggers recovery. Do not use SERVICE_CONTROL_PRESHUTDOWN for checkpointing. Its default timeout is 10 s on build 15063 and later, Microsoft says to use it only to avoid data loss, and a lab PC that hangs on shutdown is exactly the visible interference UDCS must avoid. Treat every job as killable within about 20 s, and checkpoint on a schedule while the job runs, not at shutdown. On power: SetThreadExecutionState and PowerSetRequest cannot stop a user from choosing sleep or pressing the power button. On AC power a PowerRequestSystemRequired request does block idle sleep indefinitely, so whether the agent keeps lab PCs awake must be an explicit IT policy, not something the agent defaults to. On Modern Standby, session-0 services are throttled to about 1 s of activity every 30 s, so compute cannot continue while the device is in standby. Service host: NSSM's last stable release is 2.24 from 2014, and WinSW 3.x is still a pre-release. pywin32 (PSF-2.0) or a small native wrapper keeps fewer dependencies, but pywin32 has to be installed system-wide and its DLLs must be readable by the service account. Measured on this machine: the Windows venv python.exe is a redirector that starts a second process. The service should point at the base or bundled interpreter. Bare CPython 3.12 uses about 16 MB RSS; with httpx, pydantic, psutil, ssl and pynvml loaded it uses about 34 MB. Reboot-to-restore is the biggest fleet risk. Deep Freeze wipes everything outside a ThawSpace at reboot, and its Idle Time task can restart or shut down a PC that UDCS is using. Node identity, checkpoints and the job cache must live on a ThawSpace or be fetched again from the controller. App Control for Business does not control scripts run by Python, which is not an enlightened script host, so allowing python.exe implicitly allows any .py file. Security must come from the workload account's token and sandboxing, not from application control.

- The MSI ResetPeriod column can be left empty, which means the failure count is never reset. In that case later failures map to the last Actions element, so the last action should be a restart with a long delay, not 'none', or the agent stays down for good after repeated crashes.
